# 分阶段建设与实习安排

本方案依据老师提供的建设思路组织项目：先基础，保障业务运转；后智能，提升用户体验与效率；再优化，支持数据驱动的持续运营。以下是建议实施与讲解顺序，不是已经执行的工作日报，也不表示三个阶段已经生产上线。

H5、原生微信小程序、管理后台是三个使用入口。三个入口贯穿各阶段，共用业务接口、数据库和状态规则。

## 第一阶段 先基础

首先建立完整的演艺资源服务流程，让用户能够找到资源、提交预约，让管理员能够处理业务，并让操作结果能够保存和查询。

建设内容包括账号与角色、基础用户档案、各类资源目录和详情、搜索筛选、收藏、场馆与设备档期、需求发布、评论及审核、站内消息、预约订单和售后。版权、非遗、文创、数字演出、配套服务都先作为有统一字段、可以展示与预约的资源纳入目录。

数据库、权限校验、库存与档期校验、操作日志、三端适配、错误提示从这一阶段开始建设，后续持续检查。基础数据采集和必要的订单查询也从本阶段开始，为后续分析提供依据。

阶段验收以业务流程为主：

1. 用户在H5或小程序浏览资源并提交预约，数据库保存记录。
2. 管理员确认预约，用户在另一个入口登录相同账号也能查看状态。
3. 用户执行模拟支付、确认完成；取消、退款和申诉按状态规则处理。
4. 重复档期、库存不足、越权操作和不合法输入被拒绝；评论和需求审核通过后才公开。

当前Demo已有上述代表性流程。支付、身份认证、托管、授权协议与外部渠道使用模拟方式；具体边界以 `FEATURES.md` 为准。

## 第二阶段 后智能

在基础资源、用户、订单数据能够稳定流转后，加入帮助用户选择资源、帮助运营人员处理信息的辅助能力。

建设内容包括自动标签与分群、兴趣推荐、供需匹配、运营问数、规则客服、宣传文案组合，以及设备灯位交互预览。画像先利用基础阶段的用户档案、订单、收藏与浏览记录；推荐和匹配则读取画像或需求条件。

阶段验收强调输入、结果和变化之间的联系：

1. 修改兴趣偏好后，H5和小程序推荐列表的优先顺序发生变化。
2. 选择合作需求后，返回符合分类和预算条件、同城优先的资源。
3. 用户分群能够根据模拟订单数量和交易金额计算；运营助手读取同一批业务数据。
4. 客服能够解答订单和售后问题，文案助手能够按输入主题组合内容，并明确显示模拟方式。

当前Demo采用本地规则与模板，没有接入真实大模型，也没有实现机器学习训练或真实数字孪生。后续如接入外部AI，应保留已有业务规则，独立验证回答准确性、权限范围与使用成本。

## 第三阶段 再优化

利用前两个阶段积累的记录发现问题，安排运营动作，再用后续记录检查变化。建设重点是形成“记录数据→识别问题→采取动作→再次观察”的运营过程。

建设内容包括日、周、月、季度统计、交易趋势、渠道分布、资源排名、场馆档期利用与收入分析、CSV导出、库存阈值、异常处理和操作溯源。

Demo可使用以下例子讲解这个过程：

| 观察到的情况 | 可执行的动作 | 再次检查的内容 |
|---|---|---|
| 商品库存达到预警阈值 | 后台修改库存或下架资源 | 预警是否随库存变化而更新 |
| 多笔预约待确认 | 后台确认或驳回预约 | 待处理数量、订单状态与用户消息是否更新 |
| 已支付订单出现退款或申诉 | 核实原因并执行模拟退款或调解 | 资金状态、可用库存、交易统计与日志是否一致 |
| 某类资源交易表现较好 | 调整资源供给或推荐策略，形成后续运营方案 | 后续订单及渠道数据；不能仅凭模拟数据断言真实效果提升 |
| 模拟核销、数据或舆情异常 | 查看事件并标记处理 | 事件是否从待处理列表移除，是否保留操作日志 |

当前Demo可以展示统计、规则预警、部分业务动作及其数据变化。真实营销投放、曝光归因、A/B实验、自动策略学习和真实舆情监控仍需独立建设，不能把规则演示描述为已经实现的自学习运营系统。

## 与原始需求的对应关系

阶段划分按依赖和目标组织，不把整类能力永久限定在某一阶段。同一个模块可以先实现基础部分，再逐步增加辅助与分析能力。

| 原需求领域 | 基础阶段 | 智能阶段 | 优化阶段 |
|---|---|---|---|
| 大数据分析 | 汇聚本地业务数据，建立一致字段与基础查询 | 基于规则提供运营摘要 | 多周期统计、渠道与资源分析、异常处理、报表 |
| 用户画像 | 建立用户档案，记录订单、收藏、浏览与偏好 | 自动标签、分群、兴趣推荐 | 检查分群和推荐的后续业务表现，迭代规则 |
| AI服务 | 建立可查询的业务数据与权限边界 | 运营问数、客服、文案辅助的模拟实现 | 评估准确性、响应与成本，规划真实模型接入 |
| 全区演艺资源整合 | 多类资源目录、管理、需求、沟通、预约与交易 | 供需匹配、设备交互预览 | 档期利用、交易与评价分析，调整供给 |
| 适配、易用性与安全 | 三端联通、数据保存、权限、校验、日志 | 检查辅助功能的可理解性与数据访问范围 | 持续测试、修复和运行检查 |

逐项实现情况及模拟范围仍见 `FEATURES.md` 的29项清单。

## 按成果和依赖推进

实际可用时间尚未确定，不把任务绑定到第几天。每项任务同时登记优先级、负责人、依赖、验收标准和状态；确定截止时间后再填写预计完成时间。

| 节点 | 必须交出的成果 | 验收条件 | 依赖 |
|---|---|---|---|
| M0 范围确认 | 子功能清单、分工、模拟边界、验收口径 | 所有原需求能定位负责人；未知项明确列出 | 无 |
| M1 基础业务 | 三端读取同一数据，打通资源→预约→审核→模拟支付→完成 | 正常流程可复现；权限、档期、库存检查通过 | M0；基础环境、接口与表结构 |
| M2 智能辅助 | 画像、标签、推荐、匹配、客服和文案的约定实现 | 输入变化带来可解释输出；模拟能力明确 | 对应的资源、用户或订单数据可用 |
| M3 运营优化 | 统计、导出、预警与处理联动 | 数值口径正确，处理动作能反映到状态或统计 | 对应的业务记录可用 |
| M4 集成验收 | 统一版本、跨端回归、修复记录、完整文档初稿 | 阻断演示与核心业务问题处理完，文档对应代码 | 必须交付的功能具备测试条件 |
| M5 提交准备 | 可启动源码、初始化程序、五份材料、运行说明与演示步骤 | 独立环境启动成功，演示可重复，剩余边界说明清楚 | M4 |

不同模块可以并行：例如资源数据准备好后，推荐、分析和资源文档可分别推进，不必等整个基础阶段全部结束。代码、测试和文档持续同步，所有任务都通过成果进入下一状态。

优先级建议：P0为启动、基础业务、数据一致性和阻断交付的问题；P1为需求清单中约定必须验收的其他子功能；P2为不影响验收的额外美化与增强。时间压缩时先保证P0和约定的必须交付项，范围变更要记录，不能把未实现项悄悄标为完成。

任务状态统一使用：待领取→进行中→待评审→待复测→已验收；有明确阻碍时标记“阻塞”并记录原因。提交代码、页面出现或文档写完，都不能单独代替验收。

实习可用时长不等于完整生产平台工期；报价中的人天估算按实际功能范围、模拟边界和依赖另行填写。

## 答辩演示顺序

先用一笔订单讲清基础业务：资源浏览→预约→后台审核→模拟支付→完成。再演示兴趣推荐、需求匹配与规则客服，说明这些辅助能力如何读取基础数据。最后展示交易趋势、渠道分析与库存预警，并通过修改库存或处理订单观察结果变化。

可用于项目介绍的表述：

> 本项目遵循先基础、后智能、再优化的建设路径。首先打通演艺资源展示、预约与交易管理流程，保障三端业务协同；随后基于用户和业务数据加入画像、推荐、匹配及智能服务辅助；最后通过统计分析、预警和处理反馈支持持续运营。毕业实习Demo采用模拟数据和外部接口模拟方式，重点验证流程、交互与数据联动。
